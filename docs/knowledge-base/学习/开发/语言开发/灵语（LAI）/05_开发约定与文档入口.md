# LAI 开发约定与文档入口

最后同步：2026-07-28。

## 接手顺序

1. 阅读 `docs/ai/active-context.md`、`project-brief.md`、`architecture-map.md`、`module-index.md`、`conventions.md`。
2. 确认 `README.md`、当前源码和测试是否与上下文一致；当前版本应为 v0.37。
3. 处理既有版本时读对应 `docs/superpowers/specs/` 与 `docs/superpowers/plans/`；新版本先建立设计，再开始实现。
4. 修改语法时以“测试 -> lexer/parser -> AST -> checker -> 后端 -> 文档”的顺序闭环，并保留实验性 LLVM 的能力边界。

## 验证要求

至少运行完整单元测试；涉及可执行路径时，还应运行受影响的 C/LLVM 示例：

```powershell
python -m unittest discover -v
python lai_compiler.py main.ly --run
python lai_compiler.py examples/basic_comparisons.ly --run
python lai_compiler.py examples/boolean_logic.ly --run
python lai_compiler.py examples/runtime_integer_safety.ly --run
python lai_compiler.py examples/unary_integer.ly --backend llvm --run
python lai_compiler.py examples/llvm_minimal.ly --backend llvm --run
python lai_compiler.py examples/llvm_arithmetic.ly --backend llvm --run
```

报告时分开说明：源码/静态检查、单元测试、端到端 C 验证、端到端 LLVM 验证，以及因环境未执行的项。`clang` 不在 `Path` 或 Windows 链接环境缺失时，端到端失败只说明环境需要排查，不能据此虚构编译器结论。

## v0.37 发布事实

源码保持既有关键字边界，`step` 仍是保留关键字。`int` 采用单一 checked i32 模式：纯静态零除和中间溢出在编译期诊断，动态 C 运算失败写 `stderr` 后以 `EXIT_FAILURE` 退出。`for` 固定 start/end/step 的单次求值，动态正 step 和 i32 上界范围完成由 runtime 保护；每次生成使用 collision-free 内部前缀。LLVM 的动态值和控制流仍不支持。示例是 `examples/runtime_integer_safety.ly`。

## 生成物边界

- `build/` 是生成目录，不能手工维护 `build/main.c`。
- `examples/build/*.ll`、`examples/build/*.exe` 是本地 LLVM 示例生成物，不提交。
- `.exe` 只作本机验证证据，不等同于源代码变更。
- 保留并行或用户已有改动，只暂存本任务明确的文件。

## 本地/有道云知识库与更新流程

本地可上传笔记位于：`docs/knowledge-base/学习/开发/语言开发/灵语（LAI）/`，六篇文件使用同名 UTF-8 Markdown，分别服务索引、模块、能力、架构、规划与约定。

有道云笔记是外部个人知识库，建议归档路径为 `学习/开发/语言开发/灵语（LAI）`。开始 Unity 或 Survivor 开发时需先检索有道云；LAI 本地开发仍以仓库源码、测试和 `docs/ai` 为当前事实依据。外部笔记不可用时，要明确未完成检索，不能假装已查询。

LAI 的用户可见版本或重要架构变更完成并验证后，先汇总最新开发文档并更新本地同名笔记。v0.37 的六篇笔记已同步到有道云并逐篇回读验证，远端路线图已改名为 `04_未来版本规划_v0.38-v0.44.md`；后续版本仍必须在打开远端同名笔记并核对后才能记录为已同步。

本地文档发布不等于有道云同步完成；只有远端同名笔记打开并核对后才能记录为已同步。

只有超出 LAI 版本与架构变更范围的个人知识归档才需要另行征得用户确认。项目 `AGENTS.md` 应保留 LAI 项目自身的版本同步规则，不写入与本项目无关的个人知识库约定。
