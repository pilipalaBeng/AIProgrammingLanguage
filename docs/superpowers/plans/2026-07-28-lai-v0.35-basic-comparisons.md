# LAI v0.35 Basic Comparisons Implementation Plan

Status: Completed.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete LAI's six basic comparison operators in the default C backend,
with integer ordering and same-type equality for `int`, `bool`, and `string`.

**Architecture:** Reuse the existing frozen `CompareExpr`, extend longest-match
lexing and the existing lowest-precedence comparison parser, then split checker and
C lowering by ordering versus equality semantics. Generate `strcmp` directly for
string content equality and keep the experimental LLVM capability boundary unchanged.

**Tech Stack:** Python 3.12+, standard-library `unittest`, generated C, local clang
on Windows PowerShell.

## Global Constraints

- Implement exactly `<`, `<=`, `>`, `>=`, `==`, and `!=`.
- `<`, `<=`, `>`, and `>=` accept only `int`/`int` and return `bool`.
- `==` and `!=` accept only same-type `int`, `bool`, or `string` operands and return `bool`.
- String equality is content equality generated with `strcmp`, not pointer equality.
- Preserve `CompareExpr(left, operator, right)`; do not add comparison AST node types.
- Comparison precedence stays below unary and all arithmetic operators.
- Reject a second ungrouped comparison with `line N, column M: comparison chains are not supported`.
- Permit grouped boolean equality such as `(1 < 2) == true`.
- Reject unknown direct-AST operators with `line N: unsupported comparison operator: OPERATOR` before operand lowering.
- Use `line N: ordering comparison operands must both be int, got LEFT and RIGHT` for ordering type errors.
- Use `line N: equality comparison operands must have the same type, got LEFT and RIGHT` for mixed equality types.
- Keep a standalone `!` unsupported until v0.36.
- Keep LLVM `CompareExpr` unsupported with its existing capability error.
- Do not add string ordering, comparison chaining, implicit conversions, floats, boolean logic, or pattern matching.
- Use TDD before every production-code change.
- Keep generated `build/` and `examples/build/` artifacts untracked.
- Each completed implementation task must be reviewed before the next task proceeds.

```python
_COMPARISON_TOKEN_KINDS = frozenset(
```

Use it in `_parse_expr`:

```python
left = self._parse_add_expr(allow_string, allow_name)
if self._peek().kind not in _COMPARISON_TOKEN_KINDS:

right = self._parse_add_expr(allow_string, allow_name)
if self._peek().kind in _COMPARISON_TOKEN_KINDS:
```

- [x] **Step 3: Implement checker rules**

In the `CompareExpr` branch, validate the operator before operands:

```python
ordering_operators = {"<", "<=", ">", ">="}
equality_operators = {"==", "!="}
if expr.operator not in ordering_operators | equality_operators:
    raise LaiCompileError(
        f"line {line}: unsupported comparison operator: {expr.operator}"
    )

left_kind = _infer_expr_type(expr.left, symbols, line, function_signatures)
right_kind = _infer_expr_type(expr.right, symbols, line, function_signatures)
if expr.operator in ordering_operators:
    if left_kind != "int" or right_kind != "int":
        raise LaiCompileError(
            f"line {line}: ordering comparison operands must both be int, "
            f"got {left_kind} and {right_kind}"
        )
elif left_kind != right_kind:
    raise LaiCompileError(
        f"line {line}: equality comparison operands must have the same type, "
        f"got {left_kind} and {right_kind}"
    )
return "bool"
```
