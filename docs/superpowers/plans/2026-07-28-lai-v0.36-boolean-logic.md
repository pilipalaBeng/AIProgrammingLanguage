# LAI v0.36 Boolean Logic Implementation Plan

Status: Approved for implementation.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add readable, strictly typed, short-circuiting `and`, `or`, and `not`
expressions to LAI's complete C backend while preserving the experimental LLVM
capability boundary.

**Architecture:** Add two frozen shared AST nodes, then extend the recursive-descent
parser with three logical precedence layers outside the existing comparison layer.
The checker and C lowering independently enforce strict `bool` operands; C emission
maps directly to parenthesized `!`, `&&`, and `||` so the C language preserves LAI's
left-to-right short-circuit semantics. LLVM continues to reject the new nodes with
explicit capability errors.

**Tech Stack:** Python 3.12+, standard-library `unittest`, generated C, local clang
on Windows PowerShell.

## Global Constraints

- Implement exactly the source keywords `and`, `or`, and `not`.
- `and`, `or`, and `not` become reserved keywords and cannot be variable, parameter, or function names.
- Do not support `&&`, `||`, or standalone `!`; existing `!=` longest matching must remain unchanged.
- Use frozen `LogicalNotExpr(operand)` and `LogicalExpr(left, operator, right)` AST nodes.
- `LogicalExpr.operator` accepts only `and` or `or`.
- Precedence from high to low is primary/grouping, integer unary, multiplication, addition, comparison, `not`, `and`, `or`.
- `not` is right-associative; `and` and `or` are left-associative.
- `not count < 3` means `not (count < 3)`.
- `ready or active and allowed` means `ready or (active and allowed)`.
- `not`, `and`, and `or` accept only `bool` operands and return `bool`; do not add truthiness.
- `and` and `or` must short-circuit from left to right.
- Use `line N: logical not operand must be bool, got TYPE` for invalid `not` operands.
- Use `line N: logical and operands must both be bool, got LEFT and RIGHT` for invalid `and` operands.
- Use `line N: logical or operands must both be bool, got LEFT and RIGHT` for invalid `or` operands.
- Reject unknown direct-AST operators with `line N: unsupported logical operator: OPERATOR` before operand checking or lowering.
- C lowering must defensively validate the new AST even through direct `C_BACKEND.emit()` calls.
- C emission uses `(!(operand))`, `((left) && (right))`, and `((left) || (right))` shapes.
- Keep ungrouped comparison chains unsupported with the existing parser error.
- Keep LLVM boolean, comparison, and control-flow lowering unsupported; report the new AST class name in the capability error.
- Do not add bitwise operators, logical assignment, constant folding, or LLVM boolean lowering.
- Use TDD before every production-code change.
- Keep generated `build/` and `examples/build/` artifacts untracked.
- Review every completed implementation task before starting the next one.
- Commit and push every completed task to `origin/main` after its review passes.

```python
def _parse_expr(self, allow_string: bool, allow_name: bool) -> Expr:
    return self._parse_or_expr(allow_string, allow_name)

def _parse_or_expr(self, allow_string: bool, allow_name: bool) -> Expr:
    expr = self._parse_and_expr(allow_string, allow_name)
    while self._match("OR"):
        expr = LogicalExpr(
            expr,
            self._previous().value,
            self._parse_and_expr(allow_string, allow_name),
        )
    return expr

def _parse_and_expr(self, allow_string: bool, allow_name: bool) -> Expr:
    expr = self._parse_not_expr(allow_string, allow_name)
    while self._match("AND"):
        expr = LogicalExpr(
            expr,
            self._previous().value,
            self._parse_not_expr(allow_string, allow_name),
        )
    return expr

def _parse_not_expr(self, allow_string: bool, allow_name: bool) -> Expr:
    if self._match("NOT"):
        return LogicalNotExpr(self._parse_not_expr(allow_string, allow_name))
    return self._parse_comparison_expr(allow_string, allow_name)
```

Move the existing comparison implementation unchanged into
`_parse_comparison_expr`. Parenthesized expressions continue calling `_parse_expr`,
so grouping can contain the full logical grammar.
