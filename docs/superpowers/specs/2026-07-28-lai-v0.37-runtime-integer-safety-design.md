# LAI v0.37 运行时整数安全设计

日期：2026-07-28
状态：安全模式方向已确认，等待书面设计复核后实施。

## 1. 背景

LAI v0.36 已把源码 `int` 范围固定为有符号 i32，并能在编译期拒绝一部分
显式错误，例如：

```lai
print(8 / 0)
print(-(-2147483648))
for i from 0 to 3 step 0 {
    print(i)
}
```

但是只要错误值来自变量、参数或函数调用，当前 C 后端仍会直接生成 C 整数运算：

```lai
fn divide(left: int, right: int) -> int {
    return left / right
}
```

当 `right` 在运行时为零，或者运算结果超过 i32，程序可能依赖 C 的未定义行为、
平台异常或静默错误。v0.37 的目标是让所有现有整数运算都具有确定、安全、可诊断的
行为，不增加新的 LAI 源码语法。

## 2. 已确认方案

设计阶段比较过三种整数策略：

1. **统一安全模式**：静态错误在编译期拒绝，动态错误在运行时报错并退出。
2. **固定回绕模式**：所有溢出按二进制补码回绕，除零等错误单独处理。
3. **安全/性能双模式**：由构建参数切换检查与回绕或不检查行为。

v0.37 采用方案 1。用户已确认不在当前阶段引入性能模式。统一安全模式的理由是：

- 每段 LAI 程序只有一套整数语义，结果容易复现。
- 错误包含源码行号和具体原因，便于开发者与 AI 定位。
- 不允许 C 有符号溢出的未定义行为泄漏到 LAI。
- 编译器可以省略已经静态证明安全的检查，不必增加第二套语言模式。

未来如果数值密集场景有真实基准证明需要回绕运算，应优先增加名字明确的显式操作，
例如 `wrapping_add`，而不是让整个程序切换到含糊的“不安全性能模式”。这不属于 v0.37。

## 3. i32 安全语义

LAI `int` 继续表示：

```text
-2147483648 .. 2147483647
```

下面的现有操作必须始终产生合法 i32，或者产生确定错误：

- 二元加法 `+`
- 二元减法 `-`
- 乘法 `*`
- 一元负号 `-expr`
- 除法 `/`
- 取模 `%`
- `+=`、`-=`、`*=`、`/=`、`%=`

`for` 的隐式推进不是用户写出的普通加法：当数学上的下一项已经越过固定终点时，循环
应正常结束，不能为了更新内部变量再制造一次溢出。范围循环的具体规则见第 8 节。

一元正号 `+expr` 不改变合法 i32，不需要运行时检查。

除数为零分别使用既有错误名称：

```text
division by zero
modulo by zero
```

各类溢出使用能够指出运算种类的错误名称：

```text
integer addition overflow
integer subtraction overflow
integer multiplication overflow
integer unary negation overflow
integer division overflow
integer modulo overflow
```

`INT_MIN / -1` 的数学结果超出 i32，必须报 `integer division overflow`。
`INT_MIN % -1` 在 C 和 LLVM 中也会触及有符号除法溢出边界；v0.37 为保持后端一致和
安全模式规则统一，明确报 `integer modulo overflow`，不静默返回零。

## 4. 编译期与运行时错误

完全由整数字面量、括号和现有算术节点组成的表达式继续在编译期求值。求值必须按 AST
和源码中的链式顺序检查每一个中间结果，而不只检查最终结果。例如：

```lai
print(2147483647 + 1)
print(1073741824 * 2)
print(-2147483648 / -1)
```

它们分别在编译期报对应的 `line N: integer ... overflow`。下面这种最终结果看似回到
范围内的表达式，也必须因为中间加法溢出而失败：

```lai
print(2147483647 + 1 + -1)
```

只要表达式包含变量、参数或函数调用，且无法静态证明整个运算安全，C 后端就生成运行时
检查。运行时错误统一写入 `stderr`：

```text
LAI runtime error: line 3: division by zero
LAI runtime error: line 5: integer multiplication overflow
```

随后使用 `EXIT_FAILURE` 终止进程。不得继续执行后续 LAI 语句，也不得只打印警告。

v0.37 的静态优化只覆盖纯静态整数表达式，不增加变量范围分析、循环归纳分析或构建模式。
纯静态且所有中间结果安全的表达式可以继续生成可读的普通 C 运算，不调用运行时助手。

## 5. 静态整数分析边界

`lai_int.py` 继续作为整数规则的共享模块，并新增“i32 感知”的静态求值能力。它需要
区分三种结果：

1. 表达式是纯静态且结果安全，返回 i32 值。
2. 表达式含动态节点，返回未知。
3. 表达式纯静态但出现零除数或中间溢出，返回带运算种类的确定错误。

现有 `-2147483648` 特例必须保留：正幅值 `2147483648` 只有在一元负号直接包裹及其
等价括号中合法，不能因为新增静态求值而把独立 `2147483648` 放宽为合法字面量。

`AddExpr` 和 `MultiplyExpr` 当前保存扁平 operand 列表。静态分析必须从左到右累计并
检查每一步，不能只对列表做一次 `sum` 或最终乘积检查。

## 6. C 运行时实现

`lai_stdlib.py` 新增独立的内部 C 运行时输出接口，不把这些函数暴露成 LAI 用户可调用的
标准库 API。生成的 C 代码加入：

```c
#include <limits.h>
#include <stdint.h>
#include <stdlib.h>
```

并使用静态断言确认目标 C 的 `int` 确实是 32 位。运行时提供私有静态助手：

```text
lai_i32_add(left, right, line)
lai_i32_subtract(left, right, line)
lai_i32_multiply(left, right, line)
lai_i32_negate(value, line)
lai_i32_divide(left, right, line)
lai_i32_modulo(left, right, line)
lai_require_positive_step(value, line)
lai_for_advance(current_ptr, step, end, inclusive)
lai_runtime_error(line, message)
```

加减乘使用 `int64_t` 计算中间结果，再与 `INT_MIN..INT_MAX` 比较。取负先拒绝
`INT_MIN`。除法和取模先检查零，再检查 `INT_MIN / -1` 或 `% -1`，最后才执行 C
运算，确保未定义行为不会先发生。

所有助手都是生成 C 文件内部的 `static` 函数。C 后端继续生成简单字符串，不引入
外部 Python 包、`llvmlite` 或新的大型 IR 层。

运行时助手名不能假设用户永远不会声明同名函数。每次 C 生成应创建一个局部
`CGenerationContext`：先收集程序中的函数名、参数名、`let` 名和循环变量名，再选择一个
不与任何用户标识符冲突的内部前缀。运行时助手定义、调用和内部临时变量都从该上下文
取得名字。上下文只属于当前 `generate_c` 调用，不使用模块级可变状态，因此并行或连续
编译不会互相污染。v0.37 不为用户新增保留名字前缀。

## 7. C lowering 规则

对于动态表达式，C 后端按 AST 递归生成检查调用。例如：

```lai
fn calculate(left: int, right: int) -> int {
    return left * 2 + right
}
```

生成等价结构：

```c
return lai_i32_add(
    lai_i32_multiply(left, 2, 2),
    right,
    2
);
```

链式加法和乘法保持从左到右的 AST 累计关系。复合赋值也必须使用同一助手：

```lai
count += value
```

生成：

```c
count = lai_i32_add(count, value, line);
```

因此 `count = count + value` 和 `count += value` 具有同样的溢出行为。

纯静态且已证明安全的表达式可以保留普通 C 表达式，以保持生成代码可读。v0.37 不承诺
对动态变量做范围推导；动态运算即使看起来常见，也优先走安全助手。

## 8. `for step` 与循环递增

`for` 仍只支持正向循环和正步长。规则如下：

- 省略 `step` 时使用常量 `1`，不需要非正检查。
- 纯静态 `step <= 0` 继续在编译期报 `for step must be greater than 0`。
- 纯静态正步长不生成动态正值检查。
- 起点、终点和 step 表达式都在进入循环前按源码顺序各求值一次，并保存到生成的内部
  局部变量；循环过程中不重复调用边界或 step 中的用户函数。
- 保存后调用 `lai_require_positive_step`；非正时运行时报相同规则名称。
- 循环更新使用 `lai_for_advance` 在 `int64_t` 中计算数学下一项。下一项仍在范围内时才
  写回 i32；下一项越过固定终点时返回 false，使循环正常结束。
- `continue` 仍会执行 C `for` 的 update，因此不会跳过安全推进。

示意生成结果：

```c
{
    int __lai_start_2 = start;
    int __lai_end_2 = end;
    int __lai_step_2 = lai_require_positive_step(step, 2);
    int __lai_has_next_2 = 1;
    for (int i = __lai_start_2;
         __lai_has_next_2 && i < __lai_end_2;
         __lai_has_next_2 = lai_for_advance(
             &i, __lai_step_2, __lai_end_2, 0)) {
        /* loop body */
    }
}
```

内部名称必须避开当前函数和循环体中的 LAI 用户变量。额外 C block 将临时变量作用域
限制在该循环；名称由本次编译的 `CGenerationContext` 分配，不能要求用户避开新的源码
名字前缀。

例如：

```lai
for i from 2147483646 through 2147483647 {
    print(i)
}
```

必须输出两个边界值后正常结束，不能在完成范围后报加法溢出。对于正步长和固定 i32
终点，任何超过 `INT_MAX` 的数学下一项必然已经越过终点，因此它属于正常范围结束，
不是用户可见的整数溢出。v0.37 不同时实现倒序循环、负步长语义或完整的算术 operand
求值顺序规范。

## 9. LLVM 后端边界

实验性 LLVM 后端仍只支持顶层 `print` 中的纯整数表达式，没有变量、赋值、函数调用或
控制流，因此 v0.37 不为 LLVM 新增动态运行时助手或 SSA 控制流。

共享 checker 必须在进入 LLVM lowering 前拒绝所有纯静态零除数和 i32 中间溢出，
包括加减乘、一元取负、`INT_MIN / -1` 和 `INT_MIN % -1`。安全的现有 LLVM 整数示例
继续生成并运行。LLVM 不再把源码层静态溢出作为正常回绕结果接受。

变量和动态运行时整数检查仍由 LLVM 的既有能力错误阻止，不得在文档中写成 LLVM 已经
追平 C 后端。

## 10. 错误与执行顺序

- checker 仍先完成类型检查，再判断对应整数节点的静态安全性。
- 对动态表达式，生成 C 时不得提前执行任何 LAI 函数；运行时助手只包裹生成的 C 值。
- `and` / `or` 的短路规则保持不变，位于未执行分支中的算术助手也不得执行。
- 运行时错误发生后立即退出，因此错误点之后的打印、赋值和函数调用不会发生。
- v0.37 不新增异常捕获语法，LAI 程序不能在源码中捕获这些运行时错误。

## 11. 测试范围

### 静态整数分析

- 每种算术操作的 i32 上下边界成功案例。
- 加、减、乘、一元负号、除法和取模的静态溢出。
- 链式加法和乘法的中间结果溢出。
- 静态 `/ 0`、`% 0` 和非正 `for step` 保持原有诊断。
- `-2147483648` 特例和非法正幅值保持不变。

### C 生成

- 动态加减乘、取负、除法和取模映射到正确助手并携带源码行号。
- 五种复合赋值映射到同一套助手。
- 纯静态安全表达式不生成对应运行时调用。
- 逻辑短路内的动态算术仍保留在 `&&` / `||` 的未执行 operand 中。
- 动态起点、终点和 step 各求值一次；空范围仍检查动态 step。
- 循环使用范围感知的安全推进，`through INT_MAX` 完成后正常退出。
- 内部 step 名称不会与用户变量冲突。
- 运行时助手名不会与用户函数、参数、变量或循环变量冲突。

### 真实 C 运行时

- 动态零除数、动态模零除数分别写入准确 `stderr` 并非零退出。
- 动态加减乘、取负、除法和取模溢出分别报准确错误。
- `+=`、`-=`、`*=`、`/=`、`%=` 的失败路径。
- 动态 step 为零和负数时在进入循环体前失败。
- `through` 循环到达 i32 上界后正常结束，不回绕也不产生伪溢出错误。
- 安全边界值与普通现有程序输出保持正确。

### LLVM 与回归

- LLVM 纯静态溢出由共享 checker 拒绝。
- 安全 unary 和 arithmetic LLVM 示例继续生成并运行。
- 完整单元测试通过。
- `main.ly`、比较、布尔逻辑、unary C/LLVM、LLVM minimal/arithmetic 示例全部回归。

## 13. 非目标

v0.37 不实现：

- 安全/性能构建模式或编译选项
- 静默回绕或依赖 C 有符号溢出的未定义行为
- 浮点数、新数值字面量或大整数
- 位运算与移位
- 用户可调用的 `wrapping_*` / `checked_*` API
- 变量范围分析、循环归纳分析或通用优化器
- 通用异常、错误捕获或恢复语法
- 倒序循环、负步长和 `for item in list`
- 完整算术 operand 求值顺序规范
- LLVM 变量、赋值、控制流、用户函数或动态运行时追平

下一版仍按路线图进入 v0.38 通用函数早退。v0.37 完成后剩余编号队列为
v0.38-v0.44，共 7 个待开发版本。
