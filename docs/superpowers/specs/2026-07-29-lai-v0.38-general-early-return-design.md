# LAI v0.38 通用函数早退设计

日期：2026-07-29
状态：已确认，待实施。

## 1. 背景

LAI v0.37 已能在返回值函数中使用 `return expr`，但检查器仍按“语句块最后一条
语句的形状”判断函数是否完整返回。这个模型能处理最终 `return`、完整
`if / else if / else` 返回树，以及循环体中的局部 `return`，却会拒绝最常见的
guard clause：

```lai
fn classify(value: int) -> int {
    if value < 0 {
        return -1
    }
    return 1
}
```

这里的第一条 `return` 只终止 `value < 0` 的路径；后面的兜底 `return` 对另一条路径
仍然可达。v0.38 的目标是让检查器按真实控制流判断可达性和所有路径返回，而不是继续
增加“是否为最后一句”的特例。

本版本不增加 LAI 源码语法。Parser、AST 和 C backend 已能表达并生成现有控制流，
主要改动集中在 `lai_checker.py`。

## 2. 已确认方案

设计阶段比较过三种内部方案：

1. **继续扩展最终语句规则**：在现有 `_check_final_returning_statement` 等 helper 上
   增加更多 `is_final` 和循环特例。改动看似小，但组合状态会继续膨胀。
2. **轻量控制流结果集**：每条语句返回它可能产生的控制流结果，语句块按顺序组合。
   这足以统一 `return`、fallthrough、`break`、`continue` 和静态无限循环。
3. **完整控制流图（CFG）**：先建基本块和边，再做数据流分析。扩展性最强，但超出
   当前极简编译器的实际复杂度。

v0.38 采用方案 2。它比最终语句特例更准确，又不会为了当前规模提前引入完整 CFG。

用户已确认不可达代码采用编译错误，不增加 warning 模式。错误定位到第一条不可达语句：

```text
line N: unreachable statement
```

## 3. 版本目标

v0.38 必须完成：

- 返回值函数可在顶层条件分支、嵌套分支和循环体的任意可达路径中执行 `return expr`。
- guard clause 后的外层语句保持可达，并参与所有路径返回检查。
- 同一语句块一旦没有任何 fallthrough 路径，后续第一条语句报不可达错误。
- 每个可达 `return expr` 继续执行既有返回类型检查。
- 返回值函数只有在每条可达执行路径都明确返回时才通过检查。
- 识别最小静态子集 `while true { ... }`，在循环体所有路径都返回时允许它满足函数返回。
- `break`、`continue` 和循环嵌套保持最近循环语义，不污染外层分析。
- C 后端继续直接生成已有控制流；LLVM 能力边界不扩大。

## 4. 不在范围内

v0.38 不实现：

- bare `return`、无返回值函数早退或 `main` 中的 `return`。
- `main` 返回类型、隐式返回、默认返回值。
- `if` 条件常量折叠，或把 `not false`、比较表达式证明为常量。
- 静态非空 `for` 范围证明；所有 `for` 仍可能执行零次。
- 一般终止性证明、递归终止分析或完整 CFG。
- 允许永久不返回的路径冒充“保证返回”。
- 不可达代码 warning、warning 等级或关闭开关。
- LLVM 控制流和用户函数 lowering。

## 5. 控制流结果模型

检查器内部使用一个不可变结果集合。单个结果来自以下五种状态：

```text
FALLTHROUGH  当前语句结束后可以继续执行同块下一条语句
RETURN       当前路径已从函数返回
BREAK        当前路径请求退出最近一层循环
CONTINUE     当前路径请求进入最近一层循环的下一次迭代
DIVERGE      当前路径可永久执行而不返回，也不会到达后续语句
```

结果集合表达“任一运行时路径可能产生什么结果”。例如，无 `else` 的条件早退：

```lai
if ready {
    return 1
}
```

结果为 `{RETURN, FALLTHROUGH}`；true 路径返回，false 路径继续执行。

### 5.1 语句块组合

语句块初始结果为 `{FALLTHROUGH}`，随后按源码顺序组合：

1. 如果当前结果不含 `FALLTHROUGH`，下一条语句不可达，立即在该语句行报
   `unreachable statement`，不继续检查不可达语句内部的其他错误。
2. 保留之前已经产生的 `RETURN`、`BREAK`、`CONTINUE` 和 `DIVERGE`。
3. 用当前语句的结果替换原来的 `FALLTHROUGH`。

因此 guard clause 的 `{RETURN, FALLTHROUGH}` 可以继续组合兜底 `return`，最终得到
`{RETURN}`；直接 `return` 的结果只有 `{RETURN}`，后续语句会被判定不可达。

### 5.2 普通语句

`let`、赋值、复合赋值、表达式语句、`print` 和函数调用在通过既有语义/类型检查后，
结果均为 `{FALLTHROUGH}`。

`return expr` 在返回值函数中先检查表达式类型，再返回 `{RETURN}`。在 `main` 或无
返回类型函数中继续报：

```text
line N: return is only allowed in functions with return type
```

`break` 和 `continue` 只允许在循环中，分别返回 `{BREAK}` 和 `{CONTINUE}`。循环外的
既有错误保持不变。

## 6. 分支规则

`if` 条件继续严格要求 `bool`，各分支继续使用独立符号表副本。

- 有 `else` 时，整个 `if` 的结果是 then 和 else 结果的并集。
- `else if` 继续按现有嵌套 `IfStmt` 分析。
- 没有 `else` 时，隐含的 false 路径贡献 `FALLTHROUGH`。
- v0.38 不根据字面量 true/false 删除条件分支；两个分支都按可达分支检查。

示例：

```lai
if ready {
    return 1
} else {
    return 2
}
print(3)
```

完整分支的结果只有 `{RETURN}`，因此 `print(3)` 报不可达错误。

## 7. 循环规则

循环体仍在新的局部符号表中检查。循环体产生的 `BREAK` 和 `CONTINUE` 由当前循环消费，
不会传播到外层循环或函数。

### 7.1 普通 `while`

非静态 true 的 `while` 可能零次执行，因此始终包含 `FALLTHROUGH`。循环体中的
`RETURN` 会传播到循环结果；`BREAK`、`CONTINUE` 和循环体自然结束都被当前循环消费。

例如：

```lai
fn value(ready: bool) -> int {
    while ready {
        return 1
    }
    return 2
}
```

循环结果为 `{RETURN, FALLTHROUGH}`，兜底 `return 2` 后函数结果为 `{RETURN}`。

### 7.2 静态 `while true`

v0.38 只识别 `BoolExpr(true)` 以及任意层 `GroupExpr` 包裹的 `(true)`。不识别
`not false`、比较结果或一般常量表达式。

循环体结果映射如下：

- `RETURN` 传播为循环的 `RETURN`。
- 当前循环的 `BREAK` 变成循环后的 `FALLTHROUGH`。
- `FALLTHROUGH`、`CONTINUE` 或 `DIVERGE` 变成循环的 `DIVERGE`。

所以：

```lai
fn value() -> int {
    while true {
        return 1
    }
}
```

结果只有 `{RETURN}`，可以满足函数返回要求。

下面的函数不能通过：

```lai
fn value(ready: bool) -> int {
    while true {
        if ready {
            return 1
        }
    }
}
```

它的结果为 `{RETURN, DIVERGE}`。存在永久循环但不返回的路径，因此不属于“所有路径
返回”。函数仍报既有缺少返回错误。

如果静态 true 循环包含可达 `break`，循环结果含 `FALLTHROUGH`，后面必须有兜底
`return`。内层循环的 `break` 已被内层消费，不会误伤外层证明。

### 7.3 `for`

所有 `for` 在 v0.38 中都保守地视为可能零次执行，结果始终包含 `FALLTHROUGH`，并传播
循环体可能产生的 `RETURN`。即使字面量范围看起来非空，也不在本版本做范围证明。

## 8. 返回值函数验收规则

返回值函数完成整个顶层语句块检查后，结果必须严格等于 `{RETURN}`。

- 含 `FALLTHROUGH`：存在路径走到函数末尾但没有返回。
- 含 `DIVERGE`：存在不返回也不结束的路径。
- 顶层不应残留 `BREAK` 或 `CONTINUE`；它们在循环外已经报错，在循环内由最近循环消费。

不满足时继续使用兼容诊断：

```text
line N: function <name> must end with return
```

其中 `N` 仍是函数声明行。v0.38 改进诊断语义，但不顺带修改既有错误文本。

无返回值函数和 `main` 不要求最终结果为 `{RETURN}`；它们仍允许正常 fallthrough。
不过不可达检查对所有函数统一生效，例如循环内 `break` 或 `continue` 后的同块语句仍报错。

## 9. 诊断优先级

错误按以下顺序产生：

1. 按源码顺序检查可达语句。
2. 可达语句内部的名称、类型、条件、返回类型和循环规则错误优先报告。
3. 当前结果已无 `FALLTHROUGH` 时，下一条语句只报 `unreachable statement`；不分析其
   内部可能包含的次级错误。
4. 所有可达语句检查完成后，返回值函数才检查最终结果是否严格为 `{RETURN}`。

这保留“内部类型错误优先于函数缺少返回”的既有使用体验，也让不可达诊断稳定地指向
第一条无效语句。

## 10. 实现边界

`lai_checker.py` 将用统一语句检查替换目前分离的返回函数 helper：

- 新增内部 `FlowOutcome` 枚举和不可变结果集合。
- `_check_statements` 返回控制流结果，不再只执行副作用检查。
- `_check_statement` 对所有现有 `Stmt` 返回结果集合。
- 删除 `_check_returning_statements`、`_check_final_returning_statement`、循环返回专用
  helper 等重复路径。
- 用 `expected_return_type: str | None` 统一传递函数返回上下文；`None` 表示禁止
  `return expr`。
- 保留 `loop_depth`，用于既有 `break` / `continue` 合法性检查。

不新增 AST 节点，不修改 parser token，不增加公共语言 API。`FlowOutcome` 是 checker 的
内部实现细节。

## 11. 后端行为

C backend 已能按 AST 原位置生成 `return value;`、`if`、`while`、`for`、`break` 和
`continue`，预计不需要新增 lowering。v0.38 至少用真实 `clang` 运行一个 guard clause
示例和一个静态 `while true` 保证返回示例，防止只验证到 Python 层。

实验性 LLVM backend 继续只支持空 `main` 和顶层纯整数 `print` 子集。共享 checker
放行新的 C 控制流程序，不代表 LLVM 已支持它们；使用 `--backend llvm` 时继续返回明确
能力错误。

## 12. 测试策略

新增专门的 `tests/test_lai_flow.py`，通过公共 `compile_source` 覆盖控制流行为；必要时只
修改 `tests/test_lai_compiler.py` 中已被 v0.38 有意推翻的旧断言。

核心测试矩阵：

- 单个和多个 guard clause 加最终兜底返回可以编译。
- 一侧返回、另一侧 fallthrough 后继续执行可以编译。
- 缺少 else 或兜底时仍报函数缺少返回。
- 直接 `return`、完整返回分支、`break`、`continue` 后的同块语句报不可达。
- 不可达错误落在第一条不可达语句，且优先于其内部错误。
- `while true { return value }` 和 `while (true) { return value }` 满足返回。
- 静态 true 循环中的完整返回分支满足返回。
- 静态 true 循环中的 `break`、`continue` 或部分返回不能冒充所有路径返回。
- 普通 `while` 和所有 `for` 仍需要循环后的兜底返回。
- 嵌套循环的 `break` 只由最近一层循环消费。
- 返回类型错误、void/main return、分支作用域和循环变量作用域继续回归。
- C 端到端示例输出正确；LLVM 能力错误保持清楚。

每个实现任务先写失败测试并确认失败原因，再写最小实现；任务完成后运行 focused tests、
完整 `python -m unittest discover -v` 和 `git diff --check`，独立审查通过后提交并推送。
