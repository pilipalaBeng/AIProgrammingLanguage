# LAI v0.32 Textual LLVM Backend Design

## Goal

Add LAI's first experimental LLVM backend by generating readable textual LLVM
IR for a deliberately tiny program subset, compiling the `.ll` file with the
installed `clang`, and exposing the full path through the normal CLI.

The smallest supported example is:

```lai
fn main() {
    print(42)
}
```

The expected command is:

```powershell
python lai_compiler.py examples/llvm_minimal.ly --backend llvm --run
```

It writes `examples/build/llvm_minimal.ll`, builds
`examples/build/llvm_minimal.exe`, and prints `42`.

## Chosen Decisions

### Generate Textual LLVM IR

v0.32 generates LLVM IR as readable text with the existing Python standard
library. It does not use `llvmlite`.

This keeps the first LLVM step inspectable, introduces no new dependency, and
uses the installed LLVM 22.1.8 toolchain directly. The implementation can move
to an IR builder later if control flow, SSA values, or richer types make manual
text emission difficult to maintain.

### Expose An Experimental CLI Backend

v0.32 adds:

```text
--backend {c,llvm}
```

The default is `c`, so every existing command keeps its current behavior. The
LLVM option is intentionally experimental and rejects unsupported AST nodes
with explicit `LaiCompileError` messages.

### Support Only Integer Literal Printing

The LLVM backend accepts a program with no user-defined functions and zero or
more `PrintStmt` statements whose values are `IntExpr` nodes. Supporting more
than one integer print costs no new language concept and verifies that emitted
SSA result names remain unique.

Examples accepted by the LLVM backend:

```lai
fn main() {
}
```

```lai
fn main() {
    print(42)
    print(7)
}
```

The C backend continues to support the complete current v0.31 language surface.

## Alternatives Considered

### `llvmlite` IR Builder

`llvmlite` provides structured IR construction and will become attractive when
the backend handles branches, loops, variables, and function calls. Using it in
the first experiment would add a Python-to-LLVM version relationship before LAI
has enough LLVM code to benefit from the abstraction.

### Internal API Only

The LLVM backend could be reachable only through
`compile_file(..., LLVM_BACKEND)`. This is the smallest public surface, but it
would leave users without a normal command for trying the new backend. The
chosen experimental CLI path provides a more meaningful end-to-end milestone.

### Separate LLVM Demo Script

A temporary `lai_llvm_demo.py` could avoid changing the main CLI. It would also
create a second compiler entry point that must later be removed or merged. The
normal CLI should remain the single user-facing driver.

## Architecture

The v0.32 pipeline is:

```text
source
  -> lexer
  -> parser
  -> AST
  -> semantic/type checker
  -> selected Backend.emit
  -> .c or .ll
  -> selected Backend.build
  -> native .exe
```

The backend selection changes only the final emission and build steps. The
lexer, parser, AST, and semantic/type checker remain shared.

## Module Responsibilities

### `lai_clang.py`

Add a shared function:

```python
def build_with_clang(source_path: Path, exe_path: Path) -> None:
```

It owns the existing command:

```text
clang <generated-source> -o <executable>
```

It also owns the existing clang-not-found and clang-failure error wording,
including stdout and stderr details. Moving this behavior avoids copying the
same subprocess and error handling into both concrete backends.

### `lai_c_backend.py`

Keep the existing public function:

```python
def build_c(c_path: Path, exe_path: Path) -> None:
    build_with_clang(c_path, exe_path)
```

`C_BACKEND` and all generated C behavior remain unchanged. Existing direct
imports of `build_c` continue to work.

### `lai_llvm_backend.py`

Add:

```python
def generate_llvm(program: Program) -> str:
    check_program(program)
    return _generate_checked_llvm(program)


def build_llvm(llvm_path: Path, exe_path: Path) -> None:
    build_with_clang(llvm_path, exe_path)


LLVM_BACKEND = Backend(
    name="llvm",
    source_suffix=".ll",
    emit=_generate_checked_llvm,
    build=build_llvm,
)
```

Like the C backend, the public generator checks direct callers defensively,
while the descriptor uses the private checked-AST emitter so the normal compile
path checks exactly once.

### `lai_compiler.py`

Import `LLVM_BACKEND` and define the two concrete CLI choices in one local
mapping:

```python
_BACKENDS = {
    "c": C_BACKEND,
    "llvm": LLVM_BACKEND,
}
```

Add an argparse option with `choices=tuple(_BACKENDS)` and `default="c"`. Pass
the selected descriptor to `compile_file`.

This is a fixed CLI mapping, not plugin discovery or a public backend registry.

### `examples/llvm_minimal.ly`

Add the supported integer-print example. Its generated `examples/build/`
directory remains ignored by the existing `build/` Git pattern.

## LLVM IR Shape

The example `print(42)` emits the following essential structure:

```llvm
@.fmt.int = private unnamed_addr constant [4 x i8] c"%d\0A\00"

declare i32 @printf(ptr, ...)

define i32 @main() {
entry:
  %print0 = call i32 (ptr, ...) @printf(ptr @.fmt.int, i32 42)
  ret i32 0
}
```

Each additional print uses the next unique result name: `%print1`, `%print2`,
and so on. The module omits a hard-coded target triple and data layout so clang
can apply the active host target.

LLVM `int` values use `i32` because the current C backend represents LAI `int`
as C `int`. The LLVM backend accepts integer literals from `0` through
`2147483647`; values outside this range produce a clear compile error instead
of relying on LLVM parser behavior. Negative integers are still not LAI syntax.

## Capability Validation

The normal semantic/type checker runs first. The LLVM backend then validates its
smaller lowering subset before emitting any IR.

Rules:

- `program.functions` must be absent or empty.
- Every main statement must be `PrintStmt`.
- Every printed value must be `IntExpr`.
- Every integer literal must fit signed `i32`.

Unsupported valid LAI constructs fail with the source statement line:

```text
line 2: LLVM backend does not support LetStmt yet
line 2: LLVM backend does not support StringExpr yet
line 1: LLVM backend does not support FunctionDef yet
```

An out-of-range literal fails with:

```text
line 2: LLVM backend int literal out of i32 range: 2147483648
```

Validation completes before IR lines are assembled, so callers never receive a
partial LLVM module.

## CLI Behavior

Existing commands remain C-backed:

```powershell
python lai_compiler.py main.ly
python lai_compiler.py main.ly --run
python lai_compiler.py main.ly --backend c --run
```

The LLVM experiment is explicit:

```powershell
python lai_compiler.py examples/llvm_minimal.ly --backend llvm --run
```

Argparse rejects unknown backend names. Using `--backend llvm` on a valid LAI
program outside the supported subset produces the capability error described
above.

## Error Handling

- Lexer, parser, and semantic/type errors remain unchanged.
- LLVM subset errors use `LaiCompileError` and include the source line.
- Clang-not-found and clang-failure errors remain unchanged for both backends.
- CLI catches backend errors through the existing `LaiCompileError` path.
- A failed LLVM build does not claim that an executable was built.

## Tests

Add focused unit coverage for:

- `LLVM_BACKEND` name, `.ll` suffix, emitter, and builder.
- `generate_llvm` checking direct callers.
- Exact essential IR for one integer print.
- Unique call result names for multiple integer prints.
- Empty main generation.
- User-defined function rejection.
- Non-print statement rejection.
- String, bool, name, call, grouped, and arithmetic expression rejection through
  representative AST nodes.
- `i32` upper-bound acceptance and overflow rejection.
- `build_llvm` delegating to the shared clang helper.
- `build_c` preserving its public behavior after clang extraction.
- Default CLI behavior remaining C.
- Explicit `--backend c` behavior.
- `--backend llvm` selecting `LLVM_BACKEND`.
- Unknown backend rejection.

Run full unit regression plus two end-to-end commands:

```powershell
python lai_compiler.py main.ly --run
python lai_compiler.py examples/llvm_minimal.ly --backend llvm --run
```

The first proves the full C backend remains stable. The second must write a
`.ll`, build an `.exe`, and print `42` on the installed Windows LLVM toolchain.

## Documentation

Update `README.md`, `AGENTS.md`, `main.ly` only if its current-version comment is
kept in sync, and the routing files under `docs/ai/`.

Documentation must distinguish:

- the complete current C backend surface
- the experimental LLVM subset
- the default C CLI path
- the explicit `--backend llvm` path
- unsupported LLVM lowering that is still valid LAI syntax

## Non-Goals

v0.32 does not add:

- variables or assignment in LLVM IR
- arithmetic expressions in LLVM IR
- strings or booleans in LLVM IR
- comparisons, branches, loops, user functions, parameters, or returns in LLVM IR
- SSA construction beyond unique ignored `printf` result names
- optimization passes
- object-file management
- target selection, target triples, or data-layout flags
- `llvmlite`
- JIT execution
- plugin discovery or third-party backends
- changes to LAI source syntax
