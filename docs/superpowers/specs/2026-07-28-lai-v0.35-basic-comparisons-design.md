# LAI v0.35 完整基础比较能力设计

日期：2026-07-28
状态：已确认，待实施。

## 1. 背景

LAI v0.34 已有 `<`、`>`、`==`，但三者都只接受 `int`，也没有 `<=`、`>=`、
`!=`。这会让常见边界判断、布尔值比较和字符串内容判断无法直接表达。

v0.35 补齐基础比较层，但继续保持小范围：不引入布尔逻辑、比较链、浮点数、
模式匹配或 LLVM 比较 lowering。

## 2. 已确认方案

设计阶段比较过两个主要方案：

1. 六种比较符全部只支持 `int`。
2. `< <= > >=` 只支持 `int`，`== !=` 支持同类型的 `int`、`bool`、`string`。

采用方案 2。排序关系只在已有数值类型上定义，避免给 `bool` 或 `string` 擅自规定
大小顺序；相等关系覆盖三个现有基础类型，更符合静态类型语言的常见使用方式。

示例：

```lai
let inside = count >= 0
let finished = count == limit
let changed = ready != false
let same_name = name == "JD"
```

## 3. 词法与 AST

新增三个双字符 token：

```text
<=  -> LT_EQUAL
>=  -> GT_EQUAL
!=  -> BANG_EQUAL
```

现有 token 保持不变：

```text
<   -> LT
>   -> GT
==  -> EQUAL_EQUAL
```

双字符 token 必须在单字符 `<`、`>`、`=` 之前识别。单独的 `!` 仍不是 v0.35
语法，继续报 lexer 的 `unexpected character: !`。

AST 不新增节点，继续使用：

```python
@dataclass(frozen=True)
class CompareExpr(Expr):
    left: Expr
    operator: str
    right: Expr
```

checker 和 C backend 都必须对白名单之外的 `operator` 做防御，不能把手工构造的
非法字符串直接写进 C。

## 4. 解析与优先级

表达式语法更新为：

```text
expr          := add_expr (comparison_op add_expr)?
comparison_op := "<" | "<=" | ">" | ">=" | "==" | "!="
add_expr      := multiply_expr (("+" | "-") multiply_expr)*
multiply_expr := unary_expr (("*" | "/" | "%") unary_expr)*
unary_expr    := ("+" | "-") unary_expr | primary_expr
primary_expr  := literal | name | call | "(" expr ")"
```

优先级从高到低仍为：

1. 基础表达式和括号。
2. 一元 `+`、`-`。
3. `*`、`/`、`%`。
4. 二元 `+`、`-`。
5. 六种比较运算符。

因此 `1 + 2 * 3 >= 7` 先计算算术，再比较；`(1 < 2) == true` 先通过括号产生
`bool`，再做布尔相等比较。

v0.35 不支持比较链：

```lai
1 < 2 < 3
```

parser 在看到第二个比较运算符时统一报：

```text
line N, column M: comparison chains are not supported
```

字符串字面量必须能出现在合法比较的两侧，包括 `if "A" == "A"` 和
`while name != "done"`。`if` / `while` 的最终条件类型仍由 checker 约束为 `bool`；
裸写 `if "A"` 会得到类型错误，不会成为真值语义。

## 5. 类型规则

排序比较：

| operator | left | right | result |
|---|---|---|---|
| `< <= > >=` | `int` | `int` | `bool` |

其他类型组合统一报：

```text
line N: ordering comparison operands must both be int, got LEFT and RIGHT
```

相等比较：

| operator | left | right | result |
|---|---|---|---|
| `== !=` | `int` | `int` | `bool` |
| `== !=` | `bool` | `bool` | `bool` |
| `== !=` | `string` | `string` | `bool` |

不同类型之间不做隐式转换，统一报：

```text
line N: equality comparison operands must have the same type, got LEFT and RIGHT
```

未知运算符优先报：

```text
line N: unsupported comparison operator: OPERATOR
```

该错误必须早于 operand 的递归检查，保持手工非法 AST 的错误稳定。

## 6. C 后端

`int` 和 `bool` 直接生成 C 比较：

```c
count <= limit
ready != 0
```

LAI `string` 当前映射为 `const char*`。C 的指针 `==` 不能代表字符串内容相等，
因此字符串比较必须生成：

```c
strcmp(left, right) == 0
strcmp(left, right) != 0
```

`lai_stdlib.c_preamble()` 增加 `#include <string.h>`。当前没有 `null`、FFI 或字符串
对象，v0.35 不增加空指针保护和自定义运行时 helper。

“字符串内容”沿用当前 NUL 结尾 C 字符串边界；本版不承诺嵌入 `\0` 后的数据参与比较，
也不新增 Unicode 归一化或区域排序规则。

## 7. LLVM 边界

实验性 LLVM 后端仍只支持顶层整数 `print` 子集。合法 v0.35 比较通过 checker 后，
LLVM emitter 继续稳定报：

```text
line N: LLVM backend does not support CompareExpr yet
```

v0.35 不增加 `icmp`、布尔输出、字符串常量或控制流 lowering。LLVM 比较和布尔能力
按路线图在后续后端阶段统一设计。

## 8. 兼容性

- 现有 `<`、`>`、`==` 整数源码保持行为不变。
- `CompareExpr` 结构和兼容导出入口不变。
- 旧的 `string == int` 错误会从“双方必须为 int”改成更准确的“双方类型必须相同”。
- `if` / `while` 中裸字符串会从 parser 错误变成 checker 的非 `bool` 条件错误。
- 所有生成 C 会多一个 `<string.h>` include，不改变已有程序运行结果。
- 比较函数调用 operand 的求值顺序继续沿用 C 后端既有边界，本版不承诺从左到右。

## 9. 明确不做

v0.35 不支持：

- `and` / `or` / `not` 或 `&&` / `||` / `!`。
- 比较链，例如 `1 < 2 < 3`。
- 字符串排序比较。
- 跨类型相等和隐式转换。
- 浮点数比较。
- 三路比较运算符。
- 模式匹配。
- LLVM `CompareExpr` lowering。

## 10. 验收标准

- lexer 正确区分六种比较符并遵循最长匹配。
- parser 为六种比较符生成 `CompareExpr`，并稳定拒绝比较链。
- 算术、一元和括号优先级保持正确。
- checker 完整覆盖排序与相等类型矩阵，并拒绝未知 operator。
- C 后端为 `int` / `bool` 生成普通比较，为 `string` 生成 `strcmp`。
- 合法比较可出现在 `let`、赋值、`print`、条件、参数和返回值位置。
- LLVM 对合法比较继续报明确 `CompareExpr` 能力错误。
- 新增 C 可运行示例，真实 clang 输出与预期一致。
- 完整单元测试、既有 C/LLVM 示例和默认 `main.ly` 全部通过。
