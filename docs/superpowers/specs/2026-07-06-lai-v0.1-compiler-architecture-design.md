# LAI v0.1 Compiler Architecture Design

## Goal

Refactor the LAI v0 compiler from a line-oriented regex translator into a small
structured compiler pipeline while preserving the current v0 language behavior.

The v0.1 pipeline is:

```text
source -> lexer -> parser -> AST -> C codegen -> clang
```

This release does not add new user-facing language syntax. Its purpose is to
make the next syntax additions easier, safer, and testable.

## Current Baseline

The current compiler supports:

- `fn main() { ... }`
- `let name = "text"`
- `let count = 123`
- `print("text")`
- `print(name)`

The current CLI supports:

```powershell
python lai_compiler.py main.lai --run
```

The current tests are in:

```text
tests/test_lai_compiler.py
```

v0.1 must keep these behaviors working.

## Approaches Considered

### Approach A: Keep Regex Parser And Add More Regex

This is fastest for one or two syntax additions, but it makes expression
parsing, line and column errors, and future function syntax brittle.

Decision: reject for v0.1.

### Approach B: Split Into Full Package Immediately

Create `lai/lexer.py`, `lai/parser.py`, `lai/ast.py`, `lai/codegen_c.py`, and keep
`lai_compiler.py` as a CLI wrapper. This is clean, but creates more files than
the current project needs and makes the first refactor larger than necessary.

Decision: defer until the compiler grows beyond v0.1.

### Approach C: Structured Pipeline Inside One File

Keep `lai_compiler.py` as the single compiler module, but introduce explicit
tokens, AST node classes, parser functions, and C code generation functions.

Decision: choose this for v0.1. It improves architecture without creating a big
module split too early.

## Public Interfaces

These interfaces must remain stable:

```python
class LaiCompileError(Exception):
    pass


def compile_source(source: str) -> str:
    ...


def compile_file(source_path: Path, build_dir: Path) -> tuple[Path, Path]:
    ...
```

The CLI entry point remains:

```powershell
python lai_compiler.py main.lai --run
```

## Internal Architecture

### Token Layer

Introduce a `Token` data class:

```python
@dataclass(frozen=True)
class Token:
    kind: str
    value: str
    line: int
    column: int
```

Required token kinds:

- `FN`
- `MAIN`
- `LET`
- `PRINT`
- `IDENT`
- `STRING`
- `INT`
- `LPAREN`
- `RPAREN`
- `LBRACE`
- `RBRACE`
- `EQUAL`
- `NEWLINE`
- `EOF`

The lexer should ignore spaces and tabs outside string literals. It should keep
line and column positions for error messages.

### AST Layer

Introduce focused AST node classes:

```python
@dataclass(frozen=True)
class Program:
    statements: list[Stmt]


class Stmt:
    pass


@dataclass(frozen=True)
class LetStmt(Stmt):
    name: str
    value: Expr
    line: int


@dataclass(frozen=True)
class PrintStmt(Stmt):
    value: Expr
    line: int


class Expr:
    pass


@dataclass(frozen=True)
class StringExpr(Expr):
    value: str


@dataclass(frozen=True)
class IntExpr(Expr):
    value: int


@dataclass(frozen=True)
class NameExpr(Expr):
    name: str
```

### Parser Layer

The parser accepts exactly one program shape:

```lai
fn main() {
    ...
}
```

The parser should produce `Program(statements=[...])`.

Allowed statements:

```lai
let name = "text"
let count = 123
print("text")
print(name)
```

The parser should reject unsupported syntax with `LaiCompileError` containing a
line and column where possible.

### Semantic Validation

Validation can live in the C code generator for v0.1. It should keep a symbol
table mapping variable names to value kinds:

```python
symbols: dict[str, str]
```

Required validations:

- duplicate variable names are rejected;
- unknown variable names in `print(name)` are rejected;
- `print` supports string, int, and known variable expressions;
- variable names must match `^[A-Za-z_][A-Za-z0-9_]*$`.

### C Code Generation

The generated C should remain compatible with the current tests:

```c
#include <stdio.h>

int main(void) {
    printf("Hello LAI\n");
    const char* name = "JD";
    printf("%s\n", name);
    return 0;
}
```

String variables generate:

```c
const char* name = "text";
```

Integer variables generate:

```c
int count = 123;
```

String prints generate:

```c
printf("text\n");
```

String variable prints generate:

```c
printf("%s\n", name);
```

Integer variable prints generate:

```c
printf("%d\n", count);
```

## Error Handling

v0.1 should improve error precision without changing the exception type:

```python
raise LaiCompileError("line 2, column 5: expected ...")
```

The exact wording may change, but tests should assert important phrases rather
than full messages when possible.

## Testing Strategy

Keep existing translation behavior tests and add tests for:

- token positions from `tokenize`;
- parsing a minimal `fn main`;
- AST nodes for `let` and `print`;
- preserving current C output behavior through `compile_source`;
- unknown variable and invalid syntax errors.

The test command remains:

```powershell
python -m unittest tests.test_lai_compiler -v
```

End-to-end verification remains:

```powershell
python lai_compiler.py main.lai --run
```

## Out Of Scope

v0.1 does not add:

- arithmetic expressions;
- comments;
- booleans;
- `if`;
- user-defined functions;
- type annotations;
- module system;
- LLVM IR generation;
- JIT execution.

These belong after the structured pipeline is stable.

## Success Criteria

v0.1 is complete when:

- `compile_source(source: str) -> str` still returns valid C for the current v0
  examples;
- `python -m unittest tests.test_lai_compiler -v` passes;
- `python lai_compiler.py main.lai --run` builds and runs;
- the compiler has explicit lexer, parser, AST, and C code generation layers;
- no generated files or executables are committed.
