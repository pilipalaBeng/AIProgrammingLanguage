# LAI v0.31 Backend Boundary Design

## Goal

Separate generic compilation orchestration from C-specific code generation and
toolchain invocation, while keeping the current C backend and every existing LAI
program behavior stable.

v0.31 establishes the boundary that a future LLVM backend will use. It does not
generate LLVM IR yet.

## Chosen Approach

Use a lightweight backend descriptor around the existing checked AST pipeline:

```text
source -> lexer -> parser -> AST -> semantic/type checker -> backend -> artifact
```

The descriptor carries only the information the compiler driver needs:

- backend name
- generated source suffix
- checked-AST emission function
- generated-source build function

This is deliberately smaller than a new LAI intermediate representation. The
current AST and checker are sufficient for the v0 language surface, so v0.31
does not add another compiler representation merely to prepare for LLVM.

## Alternatives Considered

### Target Branches Inside `lai_compiler.py`

The compiler driver could add branches such as `if target == "c"` and later
`if target == "llvm"`. This is initially shorter, but it leaves generated file
suffixes, code generation, and toolchain commands coupled to the driver. Each
new backend would make the entry point harder to read and test.

### Add A LAI-Specific Lower-Level IR Now

A dedicated lower-level IR could eventually support optimization, LLVM, an
interpreter, and JIT compilation. It would also duplicate part of the current
AST/checker model before LAI has enough backend diversity to define the right
abstraction. This remains a future option after at least two real backends expose
shared lowering needs.

### Lightweight Backend Descriptor

The selected approach makes backend-specific behavior replaceable without
forcing a large architecture. It preserves the readable C backend and gives the
future LLVM experiment a real integration point.

## Module Responsibilities

### `lai_backend.py`

Add this small immutable backend descriptor:

```python
@dataclass(frozen=True)
class Backend:
    name: str
    source_suffix: str
    emit: Callable[[Program], str]
    build: Callable[[Path, Path], None]
```

`source_suffix` includes its leading dot, such as `.c`. The boundary stays
function-based and minimal. `lai_backend.py` must not import a concrete backend
or maintain a global backend registry in v0.31.

### `lai_c_backend.py`

Keep C-specific ownership in this module:

- C source emission
- C output suffix
- `clang` command construction and execution
- C-specific build errors and hints
- a `C_BACKEND` descriptor used by the compiler driver

The descriptor is defined as:

```python
C_BACKEND = Backend(
    name="c",
    source_suffix=".c",
    emit=_generate_checked_c,
    build=build_c,
)
```

The existing public `generate_c(program)` entry point remains available and
continues to validate direct callers defensively. Its output must remain
compatible with the current tests.

`generate_c(program)` calls `check_program(program)` and then delegates to the
private `_generate_checked_c(program)` helper. `C_BACKEND.emit` points directly
to `_generate_checked_c` because the normal compile pipeline has already checked
the AST. This preserves defensive direct calls without checking twice in the
normal path.

The existing `_run_clang(c_path, exe_path)` logic becomes the public backend
function `build_c(c_path, exe_path)` without changing its command or error text.

### `lai_compiler.py`

Keep ownership of:

- lexer and parser
- source/file orchestration
- CLI argument handling
- running the completed executable for `--run`
- compatibility re-exports

`compile_source` gains a defaulted backend argument while preserving existing
calls:

```python
def compile_source(source: str, backend: Backend = C_BACKEND) -> str:
    program = parse_source(source)
    check_program(program)
    return backend.emit(program)
```

`compile_file` receives the same defaulted backend argument:

```python
def compile_file(
    source_path: Path,
    build_dir: Path,
    backend: Backend = C_BACKEND,
) -> tuple[Path, Path]:
```

It keeps returning the generated source path and executable path. It delegates
source suffix, emission, and native build behavior to the selected backend. The
default generated file remains `build/<name>.c`.

The private `_run_clang` implementation moves out of `lai_compiler.py` because
it is a C-backend toolchain detail. Compatibility re-export of `_run_clang` is
not required because it is private.

## Data Flow

The default C path becomes:

```text
compile_source(source)
  -> parse_source(source)
  -> check_program(program)
  -> C_BACKEND.emit(program)
  -> C source text
```

The file path becomes:

```text
compile_file(main.ly, build/)
  -> emit checked AST through C_BACKEND
  -> write build/main.c
  -> C_BACKEND.build(build/main.c, build/main.exe)
  -> return (build/main.c, build/main.exe)
```

The future LLVM path should be able to reuse this orchestration with another
backend descriptor. v0.31 does not commit to whether that backend will emit
textual LLVM IR or use `llvmlite`; that implementation choice will be presented
separately before LLVM work starts.

## Error Handling

- Parser and semantic/type errors remain `LaiCompileError` with their current
  wording.
- A backend build failure also remains `LaiCompileError`.
- Existing `clang` not-found and compilation-failure messages remain stable.
- The compiler driver must not catch or rewrite backend errors beyond the
  existing CLI boundary.

No user-visible error is added for selecting an LLVM backend because v0.31 does
not add CLI backend selection.

## Compatibility

The following behavior must remain unchanged:

- `compile_source(source)` returns generated C text.
- `compile_file(source_path, build_dir)` writes `.c`, invokes `clang`, and
  returns `(c_path, exe_path)`.
- `python lai_compiler.py main.ly --run` builds and runs the C path.
- `lai_compiler.generate_c` remains the same object exported by
  `lai_c_backend.generate_c`.
- Direct `lai_c_backend.generate_c(program)` calls still perform semantic/type
  validation.

## Tests

Add focused coverage for:

- backend descriptor fields and immutability
- the C backend descriptor using `.c`
- `compile_source(source)` preserving its C default
- injecting a fake backend into source compilation
- `compile_file` using the backend suffix, emitter, and builder rather than
  hard-coded C behavior
- C-backend `clang` errors preserving current messages
- module-boundary and compatibility re-exports

Run the full unit suite and the existing `main.ly --run` end-to-end example to
prove that the boundary refactor does not change language behavior.

## Syntax Decision Policy

v0.31 adds no syntax. For every future user-facing syntax design, development
must first present two or three practical forms when meaningful, including:

- concrete source examples
- advantages and disadvantages
- consistency with LAI's existing syntax
- relevant established-language practice
- a clear recommendation

The user chooses the final syntax before implementation. Internal refactors that
do not alter source syntax do not require artificial syntax alternatives.

## Non-Goals

v0.31 does not add:

- LLVM IR generation
- `--backend` or `--target` CLI syntax
- a backend registry or plugin discovery
- a new LAI lower-level IR
- optimization passes
- JIT execution
- changes to the LAI lexer, parser, AST, or type rules
- changes to generated C semantics or formatting
