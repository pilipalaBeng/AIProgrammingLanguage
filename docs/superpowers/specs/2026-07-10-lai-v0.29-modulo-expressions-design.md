# LAI v0.29 Modulo Expressions Design

## Goal

Add ordinary integer modulo expressions to LAI v0 while keeping arithmetic
semantics explicit in LAI instead of delegating language rules to C or LLVM.

## Scope

v0.29 adds binary `%` expressions:

```lai
let remainder = 7 % 3
print(7 % 3)
return value % 2
let value = 8 + 7 % 3
let grouped = (10 + 5) % 4
```

Modulo is valid anywhere the current integer expressions are valid:

- `let` values
- `print(...)`
- `return`
- assignment values
- `+=` / `-=` / `*=` / `/=` right-hand values
- comparison operands
- function call arguments
- `while`, `if`, `for` start/end/step expressions when the surrounding rule
  already accepts an integer expression

## Semantics

`int % int` returns `int` and follows C integer remainder behavior for now. For
non-negative operands already supported by LAI v0, this is the usual integer
remainder.

The compiler owns this LAI rule. The C backend and future LLVM backend are code
generation targets, not language-design authorities.

## Precedence

v0.29 keeps the existing minimal arithmetic precedence split:

- `*`, `/`, and `%` share the same precedence.
- `*`, `/`, and `%` bind tighter than `+` and `-`.
- `+` and `-` remain left-associative.
- `%` is left-associative for chained modulo and mixed multiplication or division.
- Parentheses continue to override grouping.
- Comparison (`<`, `>`, `==`) remains outside arithmetic expressions.

Examples:

- `8 + 7 % 3` parses as `8 + (7 % 3)`.
- `8 % 3 * 2` behaves as `(8 % 3) * 2`.
- `8 / 2 % 3` behaves as `(8 / 2) % 3`.
- `(10 + 5) % 4` preserves the grouped left side.

This is still not a full operator-precedence system. v0.29 does not add unary
operators, logical operators, floating-point numbers, or assignment expression
precedence.

## AST

Add `ModuloExpr` in `lai_ast.py`:

```python
@dataclass(frozen=True)
class ModuloExpr(Expr):
    left: Expr
    right: Expr
```

`ModuloExpr` is shared by parser, checker, and C backend. `lai_compiler.py`
continues to re-export it for compatibility with existing tests and scripts.

## Lexer And Parser

Tokenize `%` as `PERCENT`.

Update the current multiplication parser layer to parse `*`, `/`, and `%`.
`*` can keep using `MultiplyExpr(factors)` for chained multiplication, `/`
continues to build `DivideExpr(left, right)`, and `%` builds
`ModuloExpr(left, right)` while preserving left associativity.

v0.29 intentionally does not tokenize or parse `%=`.

## Type Checking

`ModuloExpr` requires both operands to be `int` and returns `int`.

Suggested errors:

```text
line N: modulo operands must both be int, got string and int
line N: modulo by zero
```

The `modulo by zero` check only covers obvious static zero right-hand operands
such as `8 % 0` and `8 % (0)`. v0.29 does not add runtime checks for dynamic
values.

## C Backend

Generate readable C:

```c
int remainder = 7 % 3;
```

Existing `GroupExpr` output preserves parentheses, so `(10 + 5) % 4` stays
grouped in generated C.

## Tests

Add tests for:

- Tokenizing `%`.
- Rejecting the unimplemented `%=`.
- `let remainder = 7 % 3`.
- `print(7 % 3)`.
- `return value % 2`.
- Function arguments using modulo.
- `8 + 7 % 3` preserving modulo before addition.
- `8 % 3 * 2` preserving same-level arithmetic output.
- `8 / 2 % 3` preserving left-associative same-level arithmetic.
- `(10 + 5) % 4` preserving parenthesized grouping.
- `ModuloExpr` AST construction and module re-exports.
- Incomplete modulo, such as `7 %`.
- Non-`int` modulo operands, such as `7 % "x"`.
- Static modulo by zero, such as `7 % 0` and `7 % (0)`.

## Non-Goals

v0.29 does not add:

- `%=`
- `count++`
- floating-point numbers
- negative integers or unary minus
- dynamic runtime modulo-by-zero checks
- assignment expressions
- full operator precedence
- LLVM IR changes
