# 0001: LAI v0 编译器范围和临时 C 后端

日期：2026-07-06

状态：Accepted

## 背景

LAI 的长期愿景包含极简语法、AI 友好能力、LLVM 优化、AOT/JIT、并发和运行时系统。
这些目标很大，不适合作为第一步同时实现。

当前仓库需要先完成一个能被普通开发环境验证的最小闭环：写 `.lai` 文件，运行编译器，
得到本机可执行文件。

## 决策

v0 只实现以下语言能力：

- `fn main() { ... }`
- `let name = "text"`
- `let count = 123`
- `print("text")`
- `print(name)`

v0 编译路径采用：

```text
LAI -> C -> clang -> native exe
```

暂不直接生成 LLVM IR。

## 原因

- C 后端便于人工检查生成结果。
- `clang` 已经能提供本机编译能力。
- 单文件 Python 编译器更适合快速试错。
- v0 的核心风险是语法、错误处理和工具链闭环，不是底层优化。

## 后果

正面影响：

- 开发和调试成本低。
- 测试可以直接断言生成的 C 代码片段。
- 端到端示例容易运行和解释。

代价：

- 当前无法体现 LLVM IR 级优化能力。
- 复杂语法会让行导向解析很快变得吃力。
- C 只是过渡后端，未来切换后端时需要重新设计中间表示。

## 后续触发条件

满足以下任一条件时，应重新评估架构：

- 需要支持表达式优先级。
- 需要多个函数和函数调用。
- 需要类型检查或类型推导。
- 需要第二个后端。
- 生成 C 的测试变得脆弱。
